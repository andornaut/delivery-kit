## Scope

Add `runner stop` and `runner start` so an operator replaces a game's runner without composing
status polls, signals and `systemctl` calls by hand. Ships in delivery-kit 7.0.0.

## Criteria

- `runner stop --game G [--timeout SECONDS]` (default 900) polls the read-only status report
  until the runner is idle and drained, then stops it with
  `systemctl --user stop delivery-kit-<game>` when
  `~/.config/systemd/user/delivery-kit-<game>.service` exists and the unit is active, otherwise
  with SIGTERM to the PID in `bus/runner.json`, only while that PID still holds the runner
  identity token. It waits for exit, verifies `runner.lock` and `loop.lock` are
  free and prints one JSON line `{schema, game, pid, method, stopped, locksFree}`. It exits 0
  when stopped with the locks free or when no runner runs (method `none`); on a timeout it exits
  1 and leaves the runner untouched.
- `runner start --game G` refuses with exit 1 while either lock is held. With the unit file it
  runs `systemctl --user start delivery-kit-<game>`; otherwise it spawns the game's installed
  `dist/cli.js run --game G` detached, with the game checkout as working directory,
  `DELIVERY_KIT_ROOT` set and output appended to `bus/runner.out`, never through `npx`. It waits
  up to 30 s for both locks and `runner.json`, then prints `{schema, game, pid, method, status}`,
  or exits 1.
- Neither command touches the delivery control state or any coordination-kit state, and both
  stay safe while another runner command runs.

## Decisions

- D1 (user, 2026-11-19): folded into delivery-kit 7.0.0 (approval reference `dk-runner-cmds`).

## Implementation notes

- "idle and drained" is the status report's top-level `drained`: no idle blocker (such as
  an active departure, a deploy retry, a CI watch or a pending request) and no reporter blocker
  (such as an uningested event log).
- the PID holds the identity when `identity_status` is `current` (runner.lock is held with
  the token `runner.identity.json` records) and that identity's `pid` equals the `runner.json`
  PID. A start is up only when the same holds and, for a spawn, the PID is the spawned child's,
  so a stale `runner.json` never counts.
- after the stop action the command waits up to 150 s for the locks, above the unit's 120 s
  `TimeoutStopSec`; `runner start` prints its error to stderr with no stdout line.
