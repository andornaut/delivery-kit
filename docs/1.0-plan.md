# delivery-kit 1.0 plan (@andornaut/delivery-kit)

Design record for delivery-kit 1.0. Implementation is on branch `v1`. File:line references cite the 0.9.x source at tag `v0.9.1`; that source is removed from `v1`.

Placement rules (user decision):

- Nothing is written outside the project folders.
- Nothing goes in `.claude` except harness-owned paths.
- The system works on both Claude and Codex.
- No Python in 1.0 (user decision). Every `libexec/*.py` and Bash mechanism is ported to TypeScript inside the single `dist/cli.js`, including the MCP channel server. Child processes are `git`, `docker`, `gh`, `wrangler`, `flock` and `claude` or `codex` status calls only.

## Durability and locking (locks kept; writes hardened)

### flock locks

| Lock                                              | Mode                                                  | Where                                                                                      |
| ------------------------------------------------- | ----------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `runner.lock` fd 5                                |                                                       | runner.sh:6-7, scheduled-once.sh:40-41                                                     |
| `loop.lock` fd 7                                  |                                                       | bus.sh:7-8, scheduled-once.sh:42-43                                                        |
| `bus-queue.lock` fd 8                             |                                                       | departure.sh:33,61, scheduled-once.sh:34,62; request.py:54-55 also takes it when capturing |
| `merge.lock` fd 9, `ci-repair-approval.lock` fd 6 |                                                       | batch.sh:6-10                                                                              |
| `ci/<sha>.lock`                                   | non-blocking                                          | ci-watch.sh:8-9                                                                            |
| `requests/requests.lock`                          |                                                       | request.py:56-57                                                                           |
| `events/state.lock`                               | blocking                                              | event.py:54-56,67-70                                                                       |
| `events/dispatch.lock`                            | non-blocking                                          | event.py:54-56,67-70                                                                       |
| `unblock/unblock.lock`                            | non-blocking for producers, blocking for the consumer | producers: unblock.py:409-412, claude_adapter.py; consumer: claude_channel.py              |
| `monitor.lock`                                    |                                                       | monitor.py:43-46                                                                           |

Detached children close fds 5-9 (bus-common.sh:113-116,124-128).

### Atomic writes

- request.py:22-35 and unblock.py:102-115 (`persist`): write a temp file, fsync it, rename, then fsync the directory.
- monitor.py:17-33: O_EXCL temp file with mode 0600, then fsync the parent and the grandparent directory.
- event.py:22-28: fsyncs the file but not the directory.
- No fsync at all: ci-watch.sh:17, scheduled-once.sh:50-56, post-push.sh:42,73-74 (`deploy-pending`) and merge.sh:116-119.

Hardened in 1.0 (decision 5). Every state write uses one `durable.ts` primitive: temp file, fsync file, rename, fsync directory. This covers the event, CI status, scheduled-slot, last-push, deploy-pending and merge writes listed above. The affected contract tests change in the same commit, and new crash tests assert the hardened ordering at each write.

### Ordering and dedupe

- The receipt is written as `sending` before the spool entry.
- The consumer claims the entry, writes the delivered record, writes the receipt as `accepted`, then unlinks.
- Events dedupe on `sha256(kind:key)`.
- A `sending` receipt with no spool entry becomes `ambiguous` and is never resent.
- Slot receipts are never retried.

## Phases

- **P0** (0.9.x): freeze the contract inventory.

## Contract harness

- CLI-level tests. `DK_IMPL=bash|node` selects an adapter that maps abstract calls to command lines.
- Fixtures: scratch `HOME` and `XDG_STATE_HOME`, plus fake `git`, `docker`, `gh`, `wrangler` and `claude agents --json` on `PATH`.
- For Bash, the adapter renders `delivery-kit.json` into bus.conf. The bus layout is identical, so file assertions are shared.
- The harness itself is written in TypeScript with vitest, matching the sibling kits, so the 1.0 repository and its CI have no Python. Unit tests that import Python modules today are rewritten as CLI-level cases. Codex cases run against the Codex adapter with a fake control socket.
- New crash tests kill the process between writes and assert the recovery state.

## `var/registry.json` (shared by delivery-kit and the skills)

```json
{
  "schema": 1,
  "revision": 42,
  "updatedAt": "2026-11-04T03:00:00Z",
  "harness": "claude",
  "host": { "nativeProjectId": "<uuid>", "root": "." },
  "roles": {
    "archies-dog-walks/tech": {
      "ownership": "active",
      "worktree": "../archies-dog-walks/.worktrees/tech",
      "branch": "claude-tech",
      "conversations": { "claude": "<uuid>", "codex": "<uuid>|null" },
      "phase": "active",
      "activation": { "marker": "<str>", "checkpoint": "var/handoffs/<scope>/<file>" }
    },
    "game-dev": {
      "ownership": "active",
      "worktree": ".",
      "conversations": { "claude": "<uuid>" },
      "duties": ["monitor", "coordinator"]
    }
  },
  "operations": {
    "archies-dog-walks": { "busOwner": "game-dev", "activation": { "marker": "<str>" } }
  },
  "transfers": [
    {
      "marker": "<str>",
      "from": "codex",
      "to": "claude",
      "phase": "source-held|accepted|active-confirmed",
      "roles": ["..."],
      "checkpoint": "var/handoffs/<scope>/<file>"
    }
  ]
}
```

Rules:

- **Keys:** a role key is `<game>/<role>` or a shared role name, and must match `config.json`.
- **Paths:** all paths are relative to game-dev.
- **Writers:** every writer holds `var/registry.lock` (flock), checks that `revision` is unchanged, writes a temp file, fsyncs it, renames, fsyncs the directory, and increments `revision`.
- **Harness:** a top-level `harness` names the active harness for all roles. Each role keeps conversation IDs per harness, so a transfer flips `harness` and does not delete the other harness's IDs.
- **Activation:** registry state does not prove activation. `transfers` carries the hold, acceptance and activation markers, as today.
- **Readers:** delivery-kit reads `harness`, `roles[*].conversations[harness]` and `operations`. It writes only `operations.*.lastAdoption` (decision 8). The skills own every other field.
- **Validation:** `delivery-kit check-config` validates `config.json`, `var/registry.json` and each game's `delivery-kit.json` together.

## Packaging, pin and loaded-code guard

### Package and pin

- `@andornaut/delivery-kit`, with bin `delivery-kit` mapped to `dist/cli.js`.
- `scripts/pack.sh` mirrors game-kit `scripts/pack.sh:17-34` and art-kit `node-package.mjs`. It runs `npm pack` in an offline container and produces `delivery-kit-<version>.tgz`, plus `SOURCE_COMMIT` (inside and beside the archive) and `SHA256SUMS`.
- Games pin `https://github.com/andornaut/delivery-kit/releases/download/v<version>/delivery-kit-<version>.tgz` as a devDependency and commit the lockfile integrity.
- The runner runs from `node_modules` in the canonical checkout. A pin changes only by a devDependency bump, then `npm ci`, then controlled idle runner replacement.

**No disk reads after startup** (needed so "finish on loaded code" holds):

- One bundled `dist/cli.js`, with only `node:` builtins.
- No dynamic `import()` and no relative `require`.
- No worker threads and no source maps.
- Templates, briefs and usage text are embedded.
- The package never spawns its own files. CI watch and event flush become in-runner tasks.
- Child processes are `git`, `docker`, `gh`, `wrangler` and `flock` only.

### Guard

- At startup the runner records the loaded version, the lockfile integrity of `node_modules/@andornaut/delivery-kit` and the sha256 of the loaded `dist/cli.js`. It writes them to `games/<g>/bus/runner.json`.
- At each departure it compares these with the installed copy.
- On a mismatch (or a missing package) it logs, emits a `pin-mismatch` event deduplicated on the loaded and installed values, and finishes on the loaded code.
- Short commands (`request`, `status`, `check-config`) load fresh code.

### Node-only load-isolation tests

- A fake `docker` gate step blocks on a FIFO while the test swaps `node_modules` from build A to build B, and in a second case deletes it. The test then asserts:
  - the push, CI and deploy events carry build id A;
  - there is exactly one deduplicated `pin-mismatch` event naming A and B;
  - the runner pid is unchanged.
- A static and spawn audit checks:
  - the bundle has no `import(` and no relative `require`;
  - the packed file list is exactly `dist/cli.js` plus metadata;
  - no child argv points under the package directory.

## State layout and migration

All mutable state lives in the ignored `game-dev/var/`:

- `registry.json` and `registry.lock`
- `route.json`
- `handoffs/<scope>/`, for example `handoffs/kits/delivery-kit/`
- `game-dev/`: review snapshots, health history, acknowledgements, retentions (from `.claude/monitor/codex`)
- `games/<g>/bus/`: today's internal layout plus `npm-cache` (from `<g>/.claude/bus`)

Runners read `<g>/delivery-kit.json` and write only to `game-dev/var/games/<g>/bus/`. The 0.x snapshots in `.claude/delivery-kit/<sha>/` stay until convergence, for rollback.

`delivery-kit migrate` is CLEANUP-marked and run from game-dev.

**Preconditions:**

- `flock -n` succeeds on the old `runner.lock` and `loop.lock`.
- `active-departure` is empty.
- No `ci/*.lock` is held.
- No request is `started`.
- No spool entry is `.claimed`.
- `deploy-pending` is absent. It holds an absolute path under the old bus.

**Steps:**

1. Hold the old queue, request, unblock and event locks plus `var/registry.lock`.
2. Copy the state in `<g>/.claude/bus/` and `.claude/monitor/codex/` to staging, preserving symlinks. This includes Tech's ad hoc approval files (`*-queued.json`, `*-ready.json`) (decision 4). Legacy scripts, `bus.conf` and the 0.x snapshots are excluded.
3. Hash both sides, fsync, rename.
4. Write `var/games/<g>/migrated.json` with the source manifest digest.
5. Build `var/registry.json` from `~/.local/state/game-sessions/libraries.json`, `shared-host.json`, each game's `.claude/session-state/game-sessions(-project).json` and the handoff checkpoints (copied to `var/handoffs/`), recording provenance per field. Source files are only read.
6. Make the old trees read-only.

**Idempotency:** a matching marker is a no-op. A changed source, or a target without a marker, stops the migration and reports. A leftover staging directory is discarded and the step redone.

**Until convergence:** a 1.x runner also takes `flock -n` on the old `runner.lock` and `loop.lock`. They are different files, so this prevents two runners.

**Convergence (removes the CLEANUP code):**

- Both skills use only `config.json` and `var/registry.json`.
- Every game completes one clean 1.x cycle: scheduled departure, CI, deploy, accepted event and ack, no `ambiguous` receipts.
- No process references an old path.

**Rollback:** at an idle boundary:

1. Stop the 1.x runner.
2. Make the old trees writable.
3. Copy back only `last-push*`, `ci/`, `deploy/` and the post-cutover receipts.
4. Start the preserved 0.x snapshot.

Queue entries are never copied back. The old registry files are never modified, so rollback needs no registry restore.

## Resident runner

Today Tech starts `project-runner.sh` detached from tmux. It runs with parent pid 1 in its own session and has an in-process 1800 s sampler and 60 s notifier.

In 1.0 the launch path runs `npx delivery-kit run --game <g>` with game-dev as its working directory. That one command resolves `config.json`, the game path and `var/`. The same loops stay in-process. No systemd, cron or new timers.

Replacement follows README:115-134:

1. Record identities.
2. Stop the idle runner.
3. Start one runner.
4. Verify there is exactly one holder of each lock, using the 0.9.0 lock probe and `runner.json`.
5. Observe the next normal slot.

## Trunk-based delivery (user decision)

This replaces the bus queue, admission records, batch scratch merges and cherry-picks in 1.0.

**Tech merges.** Tech merges each reviewed feature branch into the game's local `main`, as a real merge or a fast-forward, after its own checks. Tech does not push.

**Each scheduled departure:**

1. Take the departure lock.
2. Read local `main` HEAD (`git rev-parse refs/heads/main`) in the canonical checkout.
3. Skip if nothing is new: HEAD equals the last pushed SHA, or HEAD is a SHA whose gate already failed.
4. Create a detached scratch worktree at HEAD and run the full gate on it: uid 19001, read-only mount, tree check.
5. Push with `git push origin <sha>:refs/heads/main`. Never force. A non-fast-forward rejection is reported, and nothing is pushed.
6. Watch CI for that exact SHA.
7. Deploy on a pass.

Nothing new means nothing departs.

**Fix forward.**

- There is no cherry-pick, commit rewrite or revert.
- A red gate leaves local `main` unpushed and records `gate-failed/<sha>`, so that SHA is never re-gated. The next departure runs only after Tech merges a fix, which moves HEAD.
- Red CI or a failed deploy is likewise fixed by a new merge on top. The deploy retry state is kept.

**Kept:**

- the departure lock
- gate isolation
- the CI watch
- deploy and deploy retries
- events and reports
- the pin guard
- `runner.json`
- the scheduled wake

**Removed:**

- `bus-queue` and its lock
- admission and ready records
- batch scratch merges
- cherry-picks
- the CI-repair approval lock

**Merge commits.** Merge commits are fully supported, because the gate runs on the merged commit itself.

**`request`.** It becomes an operator-authorized one-off departure of the current local `main` HEAD, with the same rules and receipts as a scheduled departure. It never admits queue entries.

**Migration precondition.** The 0.x queue must be empty, with no admitted or ready entries, before cutover. Otherwise migrate stops and lists them for Tech.

**0.9.x.** It keeps the queue model until 1.0 is adopted, and Tech produces linear branches meanwhile.

## Harness handoff as a switch (user decision)

A Claude or Codex handoff changes one registry field. It needs no config edit, no runner restart and no migration.

### Role-name addressing

Route, `delivery-kit.json`, briefs, events and receipts name roles: `<game>/<role>` (for example `archies-dog-walks/tech`) or a shared role (`game-dev`, `art-kit`, `delivery-kit`, `game-kit`). They never name conversation IDs.

1.0 removes `REPORT_SESSION_ID`, `REPORT_THREAD`, the route's `monitor_thread_id` and `targets[].thread_id`, and the v2 route's `session_id`. The report recipient is the role `game-dev`.

### `var/route.json` (schema 1)

```json
{
  "schema": 1,
  "state": "active",
  "host": "archies-dog-walks",
  "monitor": "game-dev",
  "targets": [
    "archies-dog-walks/art",
    "archies-dog-walks/gameplay",
    "archies-dog-walks/tech",
    "chibis-way-home/art",
    "chibis-way-home/gameplay",
    "chibis-way-home/tech",
    "art-kit",
    "delivery-kit",
    "game-kit"
  ]
}
```

- `state` is `active` or `held`.
- `host` is the game whose runner dispatches the scheduled wake.
- Wake minutes and the timezone come from `config.json`.
- Every name must be a role key in `config.json`.

### Send-time resolution

Each wake, event delivery, monitor snapshot, ack and status probe reads `var/registry.json` at send time:

- the top-level `harness` (`"claude"` or `"codex"`) selects the adapter;
- `roles.<role>.conversations.<harness>` gives the conversation ID.

Nothing is cached across sends. A missing or null ID is reported `unavailable` for that role, never as clearance. Recipient decision records stay keyed by conversation ID, because a pending question belongs to one conversation; after a switch, the new conversation clears its own.

### Registry fields used

- `harness`
- `roles.<role>.conversations.claude`
- `roles.<role>.conversations.codex`
- `roles.<role>.duties`
- `revision`
- `updatedAt`

A harness flip is one `updateRegistry` mutation of `harness`, made under `var/registry.lock` by the skills' handoff command through `@andornaut/delivery-kit/registry`.

### Readiness probe

`delivery-kit status --harness <claude|codex>` sends nothing. It reports whether that adapter can deliver now:

- Claude: the `claude` executable is present and `claude agents --json` lists the sessions.
- Codex: the control socket exists and accepts a connection.
- The monitor and every route target resolve to a conversation ID for that harness.

Output is JSON:

```json
{
  "harness": "codex",
  "adapter": { "status": "available", "reason": null },
  "roles": [{ "role": "game-dev", "conversation": "<uuid>", "status": "resolved" }],
  "ready": true
}
```

It exits 0 when ready and 1 when not. The handoff preflight calls it before flipping `harness`.

### Migration

`migrate` converts the 0.x route (`monitor_thread_id`, `targets[].thread_id`, v2 `session_id`) to role names using the registry's conversation map. It stops if an ID maps to no role or to more than one.

### Tests

Both adapters are installed and tested, and the Codex parity cases are kept. Contract cases flip `harness` between two sends and assert that the second send uses the other adapter without a restart.

## Landing 1.0 on main (user decision)

- When the full suite is green (unit, v0.9.1 bash parity, and node with `DELIVERY_KIT_CONTRACT_NODE=1`), fast-forward `main` to `v1` as one merge and push.
- After that, delivery-kit work goes straight to `main` in small tested merges, and `v1` and the per-worker branches are retired.
- Release 1.0.0 only after CI is green on that exact `main` commit.
- There is no `release/0.9` branch. A blocking 0.9 issue after `main` is 1.0 is fixed forward in 1.x, and the affected game's cutover is brought forward.

## Single CLI entrypoint (user decision)

`delivery-kit <command>` (`dist/cli.js`) is the only runtime entrypoint. 1.0 removes these from the tree:

- `bin/`
- `libexec/`
- every Python and Bash test of 0.9.x

Runners, gates, CI, events, the channel MCP server and migration all run through CLI commands, and consumer wrappers call only `npx delivery-kit ...`.

The contract harness's Bash adapter runs against the extracted, checksum-verified v0.9.1 release archive instead of the tree.

Two pieces are deliberately outside the CLI:

- **`@andornaut/delivery-kit/registry`** stays a typed library export for the skills.
- **`scripts/check.sh` and `scripts/pack.sh`** stay maintainer npm scripts (`npm run check`, `npm run pack`) and are not shipped. This matches game-kit and art-kit.

Script policy (user directive):

- No Python or shell in the repository except thin build-system wrappers.
- `check.sh` and `pack.sh` are a few lines each: `exec node scripts/<x>.mjs`.
- Container orchestration and guards live in Node scripts.

## Public registry module

`@andornaut/delivery-kit/registry` is a typed public subpath export (`exports["./registry"]`). The skills use this same code once game-dev rewrites `game-sessions/scripts/start.py` in TypeScript after 1.0.

**Build.** A second bundled entry, `dist/registry.js`, plus `dist/registry.d.ts`. It uses only `node:` builtins and the `flock(1)` child process. `dist/cli.js` embeds the same source, so the runner still reads nothing from disk after startup.

**API.** Context comes first and the subject last:

- `RegistrySchema`: the types and a version-1 validator.
- `readRegistry(layout)`: a validated snapshot that carries its revision.
- `updateRegistry(layout, expectedRevision, mutate)`:
  1. holds `var/registry.lock` with flock;
  2. re-reads the registry and rejects with `RevisionConflict` if the revision has changed;
  3. applies `mutate` and validates the result;
  4. writes a temp file, fsyncs it, renames it, then fsyncs the directory;
  5. increments `revision` and sets `updatedAt`.
- `resolveConversation(registry, role)`: returns the conversation ID for the active harness.
- `loadLayout(gameDevRoot)`: reads `config.json` and resolves the `var/` paths.

**Ownership.** delivery-kit writes only `operations.*.lastAdoption`, and the module does not enforce field ownership. Contract tests cover concurrent writers, a revision conflict, a crash between write and rename, a validation failure that leaves the file unchanged, and harness-flip resolution.

**Versioning.** The registry schema and module API follow the package semver, and a schema change requires a major or minor bump with migration.
