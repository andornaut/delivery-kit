# Contract coverage

Each original 0.9 test (`tests/*.py`) mapped to its CLI-level contract case under `cases/`, or the reason it is excluded. Case tags:

- **contract**: runs on both implementations (`DK_IMPL=bash|node`) with the same assertions.
- **bash-config**: the input exists only in 0.9 `bus.conf` syntax or legacy keys; skipped on Node.
- **bash-only**: a 0.9 surface with no 1.0 CLI equivalent (export and package scripts, Python argv); skipped on Node.
- **hardened**: 1.0 durable-write ordering (plan decision 5); Node asserts the hardened behaviour, Bash the 0.9 legacy behaviour.
- **retired**: `scheduled-once` (plan decision 6), kept as a named skipped group.
- **queue-model**: the 0.9 bus queue, admission, batch, cherry-pick and CI-repair approval model. 1.0 is trunk-based (plan "Trunk-based delivery": a departure gates and pushes local `main` HEAD), so these run as Bash parity cases against v0.9.1 and are reported as `[retired: trunk-based delivery]` on Node, like `scheduled-once`. Shared cases make work available through the adapter's `offer` operation: Bash queues a branch, Node moves local `main` to the scripted commit. Assertions on batch branches, `bus-queue` contents and `merge.lock` inside shared cases are guarded by `QUEUE_MODEL`.

- **ci-disabled** and **local-remote**: 0.9 modes that 1.0 removes. 1.0 requires a GitHub slug (CI is always watched) and a remote (trunk-based delivery pushes local `main`). These run as Bash parity cases and are reported on Node as `[retired: 1.0 requires CI]` and `[retired: trunk-based delivery requires a remote]`. The CI-disabled case is status: without CI configured, an unrecorded pushed SHA is not a blocker. The local-remote cases are the queue-model request cases, whose real repositories integrate without a remote and which carry the queue-model tag. Where a 0.9 fixture used an empty remote or slug only incidentally (entry, status, cadence and native interpreter fixtures, the request ID case), it now names `origin`, and the Node adapter supplies a fixture slug for an empty one.

Fixture defaults: the fake `gh` reports the default required check (`Test`) completed and successful unless a case scripts it, because 1.0 deploys only after CI passes (0.9 calls `gh` only when a case configures a GitHub slug). On Node, a case that names no report recipient gets a registered `monitor` role with a fixture conversation, because 1.0 requires a recipient that resolves through the registry. The Node adapter also installs the built bundle as the game's pinned package, replays `runner.log` as resident output, and gives each gate worktree a fake `node_modules/wrangler/bin/wrangler.js`.

Queue-model cases: departure (eight repair approval rejections; the one-shot repair), requests (every case except the request ID validation case, because 0.9 requests capture and pin queue entries while 1.0 requests depart local `main` HEAD), status (queued branches are counted) and events (long Unicode delivery, whose long body comes from a queued branch name). The 1.0 trunk departure cases are unit tests owned by the bus port.

- **partial**: ported, with the named sub-assertion not expressible at CLI level.

The Bash adapter runs the verified v0.9.1 release, which reaches the Codex control socket through websocket-client. A receive timeout there raises `WebSocketTimeoutException`, not `TimeoutError`, so v0.9.1 records a generic failure and keeps calling where the 0.9 unit tests (with a mocked `TimeoutError`) expected a latched `native_timeout`. Four cases assert the specified latching on Node and the observed v0.9.1 behaviour on Bash (`RECEIVE_TIMEOUT_LATCHES` in `lib/cases.ts`): child health timeout, process health timeout, question state timeout and the monitor history transport failure.

Documented 1.0 decisions that change a shared case's Node expectation while Bash keeps the 0.9 behaviour (constants in `lib/cases.ts`):

- Adapter selection: 1.0 chooses the monitor adapter by the registry's active harness, not the route version. claude-route "route harness selection keeps the Codex and Claude resolvers disjoint" expects a version 1 route under a Claude registry to be rejected or deferred on Node, never the Codex path.
- Route deferral wording: `MONITOR_ROUTE_FILE` is retired for the fixed `var/route.json`, so Node expects "monitor route is unavailable or invalid; its owner must verify identities and ownership" (`ROUTE_INVALID_MESSAGE`, used by claude-route, claude-spool and unblock-guards).
- Codex queue sink: 1.0 removes the legacy `codex queue` event sink; events go only to the registry recipient through the active adapter. The three events cases that observe delivery through it (failed delivery stays durable; completion is reported once; quiet pending and retry kinds are never delivered) are reported on Node as `[retired: the codex queue sink is removed; events go only to the registry recipient through the active adapter]`.
- In-runner event flush: 1.0 flushes events inside the runner, so events "a blocked delivery holds no runner or loop lock" (a detached flusher's descriptors) is reported on Node as `[retired: events flush inside the runner; there is no detached flusher]`.
- CI poll interval: 1.0 rejects `ci.pollSeconds` 0, so the four departure CI-watch cases and two events cases poll every second on Node (`CI_POLL_SECONDS`), which the test clock keeps fast.
- Invalid configuration: 1.0 `check-config` exits 1 (`EXIT_INVALID_CONFIG`; 0.9 exits 2), in claude-events "the report recipient must resolve to a canonical session UUID" and in the entry validation cases (worker parents, deployment mode, resource caps). Usage errors keep exit 2 on both.

fsync calls themselves are not observable from outside the process without syscall tracing (the offline image has no `strace`). Hardened cases assert the observable half of the durable primitive: replacement by rename (a new inode) and no leftover temporary files.
